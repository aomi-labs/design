The problem

Onchain, an app only sees addresses.

One person — alice@gmail.com — controls a browser wallet, two embedded wallets across providers, a smart account, and a Solana address. Five public keys, one human. Treat any address as "the user" and you can't count users, rate-limit fairly, bill, or stop abuse. Continuity breaks the moment she switches wallet or device.

The fix isn't picking one wallet. It's minting an identity above all of them.

How we got here

Three architectures.

Non-custody was easy when agents couldn't act alone. Each version kept the custody promise while adding the feature the last one structurally couldn't deliver.

v1.0

Raw keys — we were a compiler

Two front doors, one amnesiac backend. You prompt in natural language ①; Aomi parses intent and compiles an unsigned transaction ②; it returns to your own popup or terminal, where the only key in the system — yours, on your device — signs and broadcasts ③. Custody was trivial because there was nothing to hold: no accounts, no sessions, no stored keys.

WHAT BROKE IT  The feature request that killed it: "schedule the task tonight, auto-sign next morning." Someone has to sign at 6am, and it can't be you. In v1 the signer is structurally a human — so unattended execution is impossible, not just missing.

v2.0

Embedded providers + account abstraction

Alice logs in with either provider ①, which mints embedded wallets — and the frontend adds an AA smart account ②. The unlock: providers support delegation. With one approval, a scoped key (A3rf4f…) is registered and lands in Aomi's KMS ③, and a background thread can now sign at 6am with nobody awake ④. The cost arrived with the feature: each provider minted its own subject, and nothing links privy-alice to para-alice. Identity fractured at exactly the moment async execution made identity matter.

↓

WHAT BROKE IT  Everything we needed next — rate limits, billing, continuity across devices, per-wallet policy — is keyed to a person. An address is not a person; a provider subject isn't either. v2 could sign for Alice but couldn't say who Alice was.

v3.0

Canonical identity + policy as data

So we mint the root ourselves. Better Auth issues one canonical aomi_uid; provider subjects, email, and SIWE-proved wallets all attach to it as signals with provenance. Wallets moved out of a mutable "current wallet" variable into a registry of durable records with explicit state — this one human-signs, this one goes through Para's MCP, this one is delegated, this one is read-only. The ACL resolver reads that registry per transaction. Identity became a graph, policy became data, and "which wallet signs?" became a query.

The insight

"Sign in with a wallet" is four separate proofs.

Most apps collapse them into one. Collapse them and you get either custody or chaos. We keep the identity plane ("who you are") apart from the execution plane ("what a wallet may sign").

The model · v3

The account graph.

We mint one canonical user ID. Every external identity, wallet, and standing approval attaches to it as a signal with provenance — how it was linked, which provider manages it, whether the connection is live or stored.

The plumbing · Sign Module

Where the wallet gets resolved.

A background thread queues transactions against public keys. At signing time, the WalletResolver reconciles two sources of truth — the live connected snapshot and the durable authorized grants — and writes the effective wallet into the tool envelope only.

The invariant. Client-facing user_state always stays the connected-wallet snapshot. Only the tool envelope ever receives the effective authorized wallet — so resolution is invisible to the client and no state gets clobbered.

The full trace · request lifecycle

One request, end to end.

A message enters at the client; the agent emits transactions; the WalletResolver picks the effective wallet from the durable grants + the live session — and then one of three things happens, per wallet policy.

The mental model · one picture

Login keys, wallets, chains, queues, signers.

The whole protocol as one graph. Pink holds keys, blue is a public key, yellow is a chain. Auth identities attach wallets; the thread's wallet × chain topology is the user state; txs queue per public key; and resolution maps every queue back to the one signer allowed to serve it.

By Alice's configuration, a tx generated for Base is built for 0x456… — and resolves to a Para signature, human-in-the-loop.
A tx generated for Solana is built for N2e3df… — authorized through Alice's Privy OAuth to be signed by a delegated key managed by Aomi.

The execution thread context loads the chain → address map; the ACL module resolves the signature consumers.

The payoff · which wallet signs?

Same thread. One user. Three signing paths.

The thread commits transactions to three of Alice's addresses. The resolver reads each wallet's policy from the account graph and routes signing accordingly — per address, per provider, per chain.

The claim, earned

The only thing we ever hold is a leash you can drop.

ScopedBound to specific wallets and actions — not your account.
Registered through the providerMinted via Privy/Para delegation, not extracted from your wallet.
Fail-closedA chain of independent checks; any failure hard-rejects the signature.

For synchronous wallets, Aomi holds nothing — the human or the provider signs. For async execution, we hold one scoped, delegated key in KMS.

Revoke it and the agent signs nothing. A standing grant is not custody. You can pull the delegation at any time, from the provider, and the auto-sign path goes dark instantly.
