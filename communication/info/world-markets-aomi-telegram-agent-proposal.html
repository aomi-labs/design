05 · Security
The necessary control behind the simple product

The agent can trade, not withdraw.

The user does not give Aomi ownership of the World account. Instead, the owner authorizes a separate trading address for a selected account. That address can submit trading actions, but it cannot deposit or withdraw, and the owner can revoke it onchain.

06 · Onchain mandate
What an onchain mandate means and why it works

The onchain mandate defines the agent’s authority.

An onchain mandate is not a promise written in the Telegram conversation. It is an enforceable authority envelope built from smart-contract-enforced policies: which World account the agent may trade, how much capital is placed in that account, whether the address remains authorized, and which venue-level risk checks every action must satisfy.

Account scope

The user chooses the account.

The owner can place the agent in a dedicated World subaccount so that its positions and available capital remain isolated from the owner’s other accounts.

Trading authority

The owner grants trade-only access.

World records the Aomi address as an authorized trader for that account. The owner keeps deposit and withdrawal authority and may revoke the trader onchain.

Risk enforcement

World checks every action.

World’s smart contracts verify the caller and apply ATLAS portfolio-risk requirements. Aomi may add narrower application rules, but those rules cannot expand the authority recorded by World.

A conversation expresses the user’s goal; the onchain mandate and its smart-contract-enforced policies determine whether the agent has authority to act.This separation is what allows the Telegram experience to feel simple without asking the user to trust the language model as the permission system.

Publishing precision: World’s public account interface proves account-scoped trade-only delegation, owner revocation, subaccount isolation, and venue-level risk enforcement. It does not yet prove arbitrary per-agent rules such as a custom asset allowlist, leverage ceiling, or drawdown limit for ordinary accounts.

Press / blog / partner newsletter

Trading on World from Telegram

A long-form announcement about the product, the onchain security model that makes delegated trading possible, and the modular architecture emerging around agentic execution.

World Markets and Aomi are working together on a straightforward product idea: give traders an easy way to use World from Telegram without moving custody, account authority, or risk enforcement into a chat interface.

The experience should feel familiar. A trader connects a selected World account, opens a Telegram conversation, and asks the agent to prepare or manage a trade using live market and account context. The agent can explain what it is doing, present the proposed action, report the result, and link the user back to the exact market, account, or position in World. The product is conversational, but the execution remains structured and verifiable.

The product

World is a fully onchain exchange deployed on MegaETH. Its interface communicates directly with smart contracts rather than relying on a centralized exchange backend to maintain balances, positions, order books, or risk state. That design means an agent does not need a private integration into a proprietary control plane. It can read the same onchain state, use the same contract interfaces, and submit the same transactions as any other compatible client.

Aomi adds the product layer that makes those capabilities useful in a conversation. A World-specific AomiApp turns contract reads and transaction interfaces into typed tools for account context, market context, order construction, and execution status. Telegram becomes the everyday surface: the user can request a limit order, inspect portfolio risk, receive a fill or liquidation warning, and return to World through a deep link that preserves the relevant context.

How the flow works

The connection begins in World, where the user is already authenticated, has selected the intended account, and can review the authority being granted. A short-lived, one-time Telegram handoff token links the browser session to the correct chat without placing sensitive account data or trading authority inside the deep link. The full intent and account reference remain server-side.

Once connected, the Aomi agent receives live, structured context rather than relying on the conversation transcript alone. It can read the selected World account, balances, available margin, positions, orders, and current portfolio risk before constructing an action. The user’s sentence is therefore an instruction, not the transaction itself. Aomi converts that instruction into a precise order request, runs the required checks, sends the approved request through the signing and transaction pipeline, and returns a status or receipt to Telegram.

The hard problem is authority

Improving the interface is the visible part of the product, but it is not the difficult part of unattended trading. The difficult question is what gives an agent the right to act when the owner is not present. A language model cannot be the permission system, and a Telegram message cannot be treated as sufficient authorization to move risk onchain.

A centralized exchange usually answers this question inside its backend. The exchange authenticates the user, stores subaccount permissions, applies risk rules, accepts or rejects an order, and controls the ledger where the result is recorded. World does not have that centralized control point. Its exchange state and execution rules live in smart contracts, so delegated agent trading must be grounded in authority that the contracts themselves recognize.

World’s onchain mandate

World already provides the core components of an onchain mandate. The owner can authorize a separate address to trade for a selected account while retaining administrative, deposit, and withdrawal authority. The owner can revoke that trader onchain without depending on Aomi, and a dedicated subaccount can isolate the capital and positions exposed to the agent. World’s ATLAS engine then evaluates portfolio-level risk and available margin as part of the venue’s execution rules.

These are smart-contract-enforced policies, not behavioral suggestions placed in a system prompt. If an agent attempts to trade an account for which its address is not authorized, the transaction cannot become a valid World action. If the owner revokes the address, the agent cannot restore its own permission. If the resulting portfolio does not satisfy World’s risk requirements, the venue remains the final enforcement boundary. The model may propose an action, but it cannot widen its account scope, grant itself custody, or override the contracts.

The Telegram conversation expresses the user’s goal. The onchain mandate determines whether the agent has authority to act, and the venue’s smart contracts enforce the final result.

This distinction matters because an onchain mandate does not mean that every possible strategy preference is automatically encoded as a dedicated account-level contract parameter. World proves the structural controls that matter most for this integration: account-scoped trading authority, owner-controlled revocation, custody separation, subaccount isolation, and venue-level portfolio-risk enforcement. Narrower rules—such as a custom asset allowlist, strategy concentration limit, or application-specific stop condition—can be enforced by the AomiApp or, where required, by an additional onchain policy module. Those application rules may narrow the agent’s behavior, but they cannot expand the authority granted by World.

A modular execution stack

The broader insight is that a production agent should not be a monolithic system that interprets language, owns keys, decides policy, and submits transactions under one trust boundary. Agentic execution becomes safer and easier to integrate when it is separated into three independent layers above the settlement rails.

Layer 01
Agent and executionAomi interprets intent, assembles live context, constructs typed actions, coordinates the workflow, and returns evidence to the user.
Layer 02
Onchain policyA venue-native mandate or an external policy provider constrains who may act, for which account, and under which enforceable risk conditions.
Layer 03
Wallet and signingAn independent provider such as Privy controls key custody and signing, so the execution partner does not need to own the wallet layer.

Beneath those three layers are the settlement rails: World’s exchange contracts and MegaETH. Settlement is where the authorized transaction changes canonical state. Each layer has a distinct responsibility, and each can be replaced or improved without forcing the others to become the entire stack. A venue such as World can supply its own onchain policy boundary; another product may outsource that function to a specialized policy provider. A wallet provider can change without rewriting the agent’s domain logic. An execution partner can improve planning and user experience without taking custody of the user’s account.

For the World integration, this modularity is especially natural. World provides a permissionless, fully onchain venue and the smart-contract-enforced controls that bound a delegated trader. Privy can provide an independent wallet and signing layer. Aomi provides the World-specific agent, typed transaction construction, Telegram orchestration, and the interfaces that connect user intent to an auditable execution path. No single component needs to pretend it can safely replace every other component.

Better UX requires serious infrastructure

“Trade from Telegram” sounds like a small interface improvement, but delivering it without sacrificing security, performance, or compatibility requires a long chain of technical decisions. The handoff must bind the correct Telegram identity to the correct World account. Tokens must be short-lived and one-time. Account state must be live and structured. Actions need unique identifiers and idempotency protection. Policy evaluation must occur outside the language model. Signing authority must remain isolated. Transactions need simulation or preflight checks, deterministic construction, submission tracking, receipts, and post-execution state verification. Revocation must work even when the agent runtime is unavailable.

The integration must also meet the existing financial stack where it is. That means using contract ABIs, typed SDKs, familiar account and order schemas, and explicit transaction boundaries instead of asking a venue to replace its infrastructure with an agent-specific backend. Good agentic infrastructure enriches the product that already exists; it does not erase the security and operational decisions that made the venue credible.

What this partnership represents

World Markets and Aomi are early adopters of a more mature approach to agentic crypto. World shows how a venue can expose permissionless execution while keeping authority and risk enforcement onchain. Aomi shows how an execution partner can turn those primitives into a useful product across Telegram and the web without becoming the wallet, the custodian, or the policy sovereign.

The opportunity is larger than adding a chatbot to an exchange. It is to establish an architecture in which agents can improve how people interact with financial products while remaining bounded by independently enforced authority. Many teams can demonstrate a model producing a transaction. The teams that productionize this category will be the ones that can connect identity, context, policy, signing, execution, and receipts into one understandable user experience—without collapsing those responsibilities into a single point of trust.

That is the implementation choice behind the World trading agent: make Telegram simple for the user, keep the execution path modular for builders, and keep the authority where it belongs—inside an onchain mandate enforced by smart contracts.
