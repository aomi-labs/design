The shape of it

Two charging arms, one derived ledger

The money system has two ways to charge and one book that reconciles them. The arms share vocabulary — an app's pricing.toml declares prices for both — but never share a settlement path. One moves credits off-chain; the other rides the user's own transaction on-chain.

Arm 1 · charged to the user
Turn charging
  • Charges forCompute — model tokens + priced tool calls
  • UnitAomi credits, off-chain
  • CollectedHTTP rail — x402 prepaid or Tempo postpaid
  • Ledgerllm_usage_events
Arm 2 · charged to the user
Outcome charging
  • Charges forA successful on-chain action's end-state
  • UnitThe flowed token itself, on-chain
  • CollectedA fee leg inside the user's own AA batch
  • LedgerThe chain — receipts on user_transactions
Derived ledger · platform ↔ builder statement_entries reconciles both arms plus hosting into what the platform bills the app builder — priced by the platform take rates in rates.toml. It is Aomi's statement to the builder, never a user-facing rail.
Part I — What a user pays

How a turn gets paid

At admission the resolver picks one rail for the turn. Absent a ?payment_method= override it walks a fixed default chain and takes the first that can service the turn; an explicit method is exclusive and returns a 402 challenge if it can't pay.

Quotanull
Tier allowance

The user's included Aomi allowance. No stream channel, no BYOK key — quota rows carry the null sentinel on the usage ledger.

BYOKbyok
Own provider key

The user's own model-provider key pays the provider directly. Aomi credits are not consumed — model tokens are waived for the turn.

Tempo / MPPtempo
Postpaid — settled after the turn

A payment channel opened at the gate; the runtime settles the real charge against it once the turn completes, via Settler::settle.

Coinbase x402coinbase
Prepaid — settled at HTTP time

The gate settles before the turn runs; the cleared amount lands on the row's paid_credits and the settlement receipt returns to the client.

Default resolution: quota→ byok→ tempo→ coinbase
Underwater floor  A paid user runs a tab before being challenged. Platform debt accrues to a default of 500 credits ($5) before a model/fee x402 challenge fires; each external partner bucket accrues to 100 credits ($1) before its own recipient-targeted challenge.
Part I · Arm 1

Turn charging credits · off-chain

Two things accrue during a turn: the model tokens it burned, and any priced tool calls it made. Both fold into the turn's credits_used and land on llm_usage_events.

How the buckets are priced

A turn's tokens split into buckets, each priced off the model's rate:

Uncached inputFull input rate.
Cached-input readDiscounted per-model cache-read rate — e.g. Opus $0.50/1M vs $5.00 base; Sonnet $0.30; Haiku 4.5 $0.10.
Cache creationInput rate × 1.25 for Anthropic models; input rate otherwise.
Visible outputFull output rate.
Reasoning outputBilled at the output rate, same as visible tokens.
Tool-call flat feeA per-call constant, currently $0 in production (the knob exists; the rate is zero).
BYOK waiver  On a BYOK turn the model buckets above are waived entirely — the user's own provider key already paid the provider, so no credits are consumed and no model bill line is written.

Priced tool calls

An app declares a flat per-call price for a tool in its pricing.toml [resources.*] block. Each call that succeeds mints one charge line; a call blocked before dispatch or returning an error envelope is never charged.

price_µUSD = fix + base × factor / 10,000   // V1 uses fix only; base·factor reserved for cost-plus
Fail-closed  Quota and BYOK turns get a zero tool budget — priced tools require a collectable rail (x402 or Tempo) and are refused otherwise. Free tools are unaffected.
Part I · Arm 2

Outcome charging token · on-chain

When an app moves value for the user, it can take a fee on the amount that flowed. This never touches credits — it's an extra transfer leg appended to the user's own transaction, paid in the flowed token, and it executes if and only if the transaction does.

The rule

An app's [[outcome]] block declares an effect, a fee in basis points, and a beneficiary. Today the only effect is flow — value moved by a transfer or swap input. Bps must be 1..=10,000 (100% ceiling).

fee = flow × bps / 10,000   // in the flowed token, decimal base units

How it settles

At commit, each stamped flow becomes an AaCall fee leg — a native value send or an ERC-20 transfer to the beneficiary — appended to the same UserOp as the user's action. No credits, no 402, no gate. The receipt watcher then confirms execution and stamps transfers / fee onto user_transactions.

Boundaries  A fee that floors to zero (dust) writes no leg; an unresolved beneficiary is inert. Outcome fees are EVM-AA only today — SVM outcome fees are not built.
Part II — What an app pays

The builder statement platform ↔ builder

Everything above is charged to the user. Separately, Aomi bills the app builder through a derived ledger, statement_entries, priced by four platform take rates. These are the committed source of truth in rates.toml — the parsed struct is the biller, and a unit test pins the file to its defaults so it can never reprice silently.

10%
Tool take

Platform take on the gross of a builder's paid tool call (x402).

tool_take_rate = 0.10
30%
Outcome take

Platform take on a builder's outcome fee — the on-chain bps-of-flow.

outcome_take_rate = 0.30
10%
Managed-model markup

Markup on base model cost for apps using platform-managed keys. BYOK apps pay 0 — no bill line is written.

managed_model_rate = 0.10
$10/mo
Hosting

Flat charge per app per calendar month. The whole charge is the platform's fee.

hosting_usd_month = 10.0

How amounts are written

modelgross = base × 1.10 ·  fee = base × 0.10 ·  net = −gross. Written post-turn for managed-key turns; live.
hostinggross = fee = $10.00 ·  net = −$10.00. Flat monthly; live.
tool_invocation10% of the paid tool call. Schema reserved — no writer yet.
outcome30% of the outcome fee. Schema reserved — no writer yet.

Charges carry a negative net by convention (the builder owes), and a future settlement job flips each row's settlement flag when it's collected.

Whose pocket each fee lands in

A worked example

Same turn, followed all the way through — with each charge's effect on all three balances. The three layers are not one waterfall; they settle on separate paths to different parties.

Compute · Arm 1 User → Platform  (platform then pays the model provider). Cash, on the user's rail.
Outcome · Arm 2 User → App  directly on-chain. The platform is never in the settlement path.
Statement App → Platform, reconciled later. Only model + hosting are live today; the take rates are reserved.
A user on the Coinbase x402 rail asks a partner app running on a platform-managed Opus 4.8 key to place a $1,000 ETH swap. The turn burns 40K input + 8K output tokens. The app prices its place_order tool at 1.0 credit and declares a 10 bps outcome fee to its own beneficiary.

Reconciles to zero The user pays $1.41 total. Of the platform's +$1.097, roughly $0.36 flows straight out to the model provider (external), leaving its real margin. The app takes in +$1.01 (its tool fee + the on-chain outcome) and owes back the managed-model bill and — once wired — the take rates, netting +$0.31 on the turn. Add a flat $10.00/month hosting charge on the app's statement, amortized across every turn, not booked to this one.
Worth a second look The model is recorded on two ledgers at once — the user's compute charge (Arm 1, $0.40) and the builder's statement ($0.396). On a managed-key partner turn the platform books the model on both the retail and wholesale side. If the intent is that the app resells Aomi (user on the app's allowance, builder pays wholesale), one of these two should be zero — worth confirming against background.rs before this is the story we tell partners.

The pattern across all four Today the platform's live revenue is model margin + hosting + any first-party outcome. The two big third-party levers — 30% of outcome and 10% of tool fees — are designed but reserved (no writer yet). So the app's usage shape decides whether the platform monetizes it today: hosting-heavy and first-party apps pay now; outcome-heavy and tool-heavy third-party apps mostly don't, until those takes are wired.
