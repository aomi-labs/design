x402 payment processing

Deferred Credit Gate

Instead of verifying payment on every API turn, we keep a running credit balance and only re-check it at a checkpoint every TURN_CAP turns. Between checkpoints the balance is allowed to run negative — turns keep flowing, and the user isn't billed each time.

credit0 = 1 TURN_CAP = 3 cost / turn = 5 gate: balance ≥ 0

Running balance across turns

The amber rail is the pay gate — a request clears only while balance ≥ 0. But the gate is only checked at a checkpoint (every TURN_CAP turns). Turns 2 & 3 ride through on credit; the debt is caught when the gate slams shut at turn 4.

pay gate · request clears if balance ≥ 0 checkpoint · gate open → serve in-window turn · no check, serve on credit checkpoint · gate shut (balance < 0) → 402 balance trajectory · top-up lifts it back through

Normal x402

Gate on every call.

  • Balance checked before every turn — the classic per-request 402 gate.
  • A settlement / billing event fires every turn → chattier, slower.
  • Zero credit exposure: a request never runs while below zero.
deferred · CAP 3

Our deferred gate

Gate once per TURN_CAP.

  • 2 of 3 turns skip the gate → fewer round-trips, fewer bills, faster.
  • Balance may run negative between checkpoints; caught at the next gate.
  • Even a user starting at 0 flows — set CAP=1 to recover strict x402.

x402 vs MPP — same accounting, different gate position

The credit/turn-cap bookkeeping is agnostic. The two variants differ only in when the balance check runs relative to the API call.

x402

Pre-check gate

Verify before serving.

  • Check runs ahead of the API call at each checkpoint.
  • Fails closed: 402 Payment Required blocks the call.
  • Payment headers negotiated up front, then the response is served.
MPP

Post-check settle

Verify after serving.

  • API call runs first; the balance check happens after.
  • Serve-then-settle — reconcile on the trailing edge.
  • Same running-balance + TURN_CAP math underneath.

Outcome-based pricing — settle on what actually happened onchain

What's next. Flat pricing bills the same per API call — no matter what that call actually does on-chain. The richer model prices each turn on its realized on-chain side-effects: the turn's smart-contract calls are replayed inside an isolated chain head in our hosted runtime, and the settlement is adhered to the metered outcome before it commits to canonical state.

Why Aomi is a blockchain harness built around execution. The value of a turn is in what it does on-chain — so it makes sense for us, and for the apps running on us, to charge for on-chain side-effects, not just API round-trips.
How · AA Settlement rides account abstraction. Say an app managing a Morpho pool emits three on-chain calls in one turn — wrap ETH, deposit, transfer. We treat them as user-ops and batch them into a single account-abstracted Tx. The outcome is the simulation result of those first three calls; we then adhere a fourth call — the payment — routed to the treasury of the app's operator.
app's on-chain calls · user-ops (wrap · deposit · transfer) adhered payment op · priced on outcome → operator treasury isolated chain head · sandboxed simulation

Same turn, two pricing models — flat bills a constant per API call; outcome-based rides the realized on-chain effect:

flat · today

Flat per-API-call pricing

One price per API call, whatever it does on-chain.

  • A read-only call and a call that moves funds on-chain are billed identically.
  • Simple to reason about — the current x402 / credit model.
  • Leaves value on the table and can under-price risky on-chain effects.
simulation engine

Outcome-based pricing

Priced on the measured on-chain outcome.

  • Batch the turn's on-chain calls as user-ops into one account-abstracted Tx.
  • Simulate ops 1–3 in an isolated chain head; meter every side-effect.
  • Adhere a 4th payment op priced on the outcome → the operator's treasury.
✓ Payment-header plumbing is implemented and shared across both variants — the gate is x402 + MPP agnostic. Swapping variant only moves the check from before the call (x402) to after it (MPP).
