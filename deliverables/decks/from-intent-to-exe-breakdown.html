What Claude will do
1Research — figure out what's needed
  • Search the docs for the right contract: which router, which version, on which chain
  • Find the deployed address, and check it's the real one, not a clone
  • Read the ABI and source; if it's a proxy, chase the implementation
  • Token details: which USDC on Base, 6 decimals, is an approval needed first
2Take action — then realise it needs more
  • Chain RPCpublic endpoints rate-limit; ask you for an Alchemy key
  • Etherscan APIanother key, or paste the ABI in by hand
  • Simulation endpointan Anvil fork or Tenderly, or skip it and hope
  • A revert comes back as raw bytes: decode it, edit the script, run again
3Signing — the question nobody wants to answer
  • Would you paste your private key into Claude's .env?
  • Is there a policy? Nothing caps the amount except Claude's own judgement
  • --dangerously-skip-permissions: one flag, and cast send just runs
An external skill can help with each of these — but it can't skip the steps towards landing a correct transaction.

What Aomi will do
1Research — already there, out of the box
  • Loads the skills the intent needs: lido, aave, common_erc20

  • Reads live state directly: 10 ETH, nonce 2751, 1 stETH → 0.8059 wstETH

  • Chain RPCits own node across 10+ chains; no key to ask you for
  • Contract codeget_contract from the DB; no pasting ABIs by hand
  • Simulationeach leg on a fork of mainnet, then all 6 end to end: all pass

3Signing — one bundle, your wallet
  • 6 txs → 1 bundle with account abstraction: stake, approve, wrap, approve, supply, borrow
  • One signature in your existing wallet; keys never leave it
  • Policy lives in the runtime, not the model: manual, auto-approve or bypass
A harness is the loop around the model: what it can read, what it can write, and what it takes to commit.

Where the intelligence lives

Frontier models decode intent to protocols like an ordinary crypto engineer.

“I want yield” → Aave. “Cheapest route to Arbitrum” → a bridge aggregator. “Hedge this” → a perp venue. The mapping from human goal to protocol is common knowledge now, and where it isn't, the model searches the web the way a researcher would.

This step needs no infrastructure from us. It's also where most “AI × crypto” demos stop — and it's the easy part.

The read path · what the model calls
get_contract(addr, chain)
ABI + verified source. DB cache hit → return; miss → Etherscan fetch, store back, resolve the proxy (EIP-1967) so the model sees the implementation, not the shell.
get_account_info(addr, chain)
balance, nonce, code — one call, one gateway.
encode_and_call(sig, args, to)
any view function: balanceOf, getReserveData, quoteExactInput. Encoded, eth_call'd on the fork, decoded, unit-formatted.
format_*
raw 32-byte words → “2,400.00 weETH”. The model never divides by 10¹⁸.
Why a general agent loses here

Vertical integration turns twelve round-trips into one.

Claude with a browser reads Etherscan HTML, guesses the proxy, pastes an ABI into a script, then runs it. Every hop costs tokens, time and a chance to be wrong. Aomi's readers are cached, chain-aware and pre-decoded, so “what is the current supply APY on Aave for WETH?” is one tool call and ~200 ms.

What actually happens · the loop

A chain fork is CI for transactions.

Inside Aomi, every encode_and_call is an eth_call against a sandboxed fork of live state. A revert comes back to the model as back pressure, the way red tests push back on a coding agent. Only a green run gets committed.

Aomi — the fork runs the call; the chain only sees what passed
Coding agent — CI runs the code; main only gets what passed

The security-critical boundary

commit_txs is the only door out.

Everything before it is rehearsal in a fork. Once the model commits, it is delivering signable transactions to a human or a wallet policy. No other path leads to a chain.

Coding agents taught everyone the pattern: read, write, then commit through a gate you don't control. Onchain it's the same shape — the gate is the signer.

Mode 1

Manual

Every committed transaction goes back to the user's own wallet to sign. Browser wallet, Para, Privy — whatever they already have.

Mode 2

Auto-approve

No key on the server. A browser or CLI session signs with a scoped JWT, inside limits the user set. DCA, rebalances, limit orders.

Mode 3

Bypass permission

👛
Agent wallet

Held by the runtime, stays in a TEE. The model never sees the key; it signs within caps, revocably, with an audit log. For agents that are users themselves.

Future direction

Onchain policy contract

A smart account that says “if this tx touches an OFAC-sanctioned address, revert.” Policy enforced by the chain itself — not by the runtime, not by the model.

Signing is necessary and commoditised. The harness's job is to hand it a transaction that deserves to be signed.

The one thing a harness adds

Verify the outcome against the rehearsal.

  • Expected vs. actual — the simulated state diff the user approved is compared with the post-inclusion state. Same Δ balances, same positions.
  • Idempotent — a retry can never double-execute; the staged bundle has one identity.
  • Execution record — instruction → policy decision → simulation → authorization → receipt, kept as one evidence chain. That's what a treasury or a fund actually audits.
Settlement is the chain's job. Reconciliation — proving intent became outcome — is the harness's last job.
